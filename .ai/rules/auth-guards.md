# Auth Guards

> **Header note, 2026-09-03 (Phases 1 & 4 of `.claude/plans/archive/humming-nibbling-flame.md`).**
> Two things below describe deleted code; the mechanisms they illustrate are
> preserved and, for logout, still exactly how the current fix works.
>
> - **`UpdateUserLastSeenMiddleware` and the whole `last_seen_at` leg are
>   gone** (deleted Phase 1, alongside `packages/filament`'s tenant panel,
>   the only place that registered it — see `.ai/rules/index.md`'s middleware
>   note). The bullet below and its "Suggested better approach" are pure
>   history now; no `last_seen_at` write path exists to retarget the wrong
>   connection.
> - **`POST /logout` is Fortify's route now, not `routes/auth.php` (deleted,
>   folded into `routes/web.php` in Phase 3, then superseded by Fortify's own
>   route loading in Phase 4).** `Actions\Auth\LogoutUser::handle()` is no
>   longer what runs on that path — `AuthenticatedSessionController::destroy()`
>   is, and it only logs out `config('fortify.guard')`.
>   `Listeners\Auth\EndOtherGuardSession` (registered with an explicit
>   `Event::listen(Logout::class, ...)` in `packageBooted()`, since Laravel's
>   listener auto-discovery never scans a package's `src/`) covers the other
>   guard instead, firing on the `Logout` event `SessionGuard::logout()`
>   dispatches before invalidating the session. **The mechanism the bullet
>   below documents — resolving the tenant guard outside tenant context reads
>   the *central* `users` table, and `SessionGuard::logout()` resolves before
>   it clears — is exactly why the listener still ends the tenant session by
>   forgetting the guard's session key and recaller cookie directly, never
>   calling `logout()`, outside tenancy.** `Actions\Auth\LogoutUser` still
>   exists, trimmed to a plain `handle(): void` for non-HTTP callers
>   (`Livewire\Actions\Logout`, tests) — read the bullet's mechanism as
>   current, its call sites as history. See `.ai/rules/auth-login.md` for the
>   listener's own docblock-level detail.

- **Invariant: central domain default guard = central guard, inside tenant = tenant guard.** Enforced by `Nvade\Numerosis\Services\Tenancy\Bootstrappers\AuthGuardBootstrapper`, registered in `config('tenancy.bootstrappers')`, calls `Auth::shouldUse()` on bootstrap, restores previous guard on `revert()`. `AuthManager::shouldUse()` rewrites both `auth.defaults.guard` *and* manager's `userResolver`, so `auth()->user()`, `$request->user()`, `@auth`, `Gate`, policies all follow automatically. Before this: rule was convention only — code opting into `TenancyAwareGuard` got it right, everything else silently resolved `CentralUser` on tenant domains.

- **`web` *is* central guard.** No guard named `central` — one existed alongside `web`, backed by duplicate `central` provider over same `CentralUser` model, deleted because nothing called `Auth::guard('central')` and two session guards over one model = user authenticated under one, not other. `web` keeps Laravel's default name so framework/package defaults land on it. App code names it `config('numerosis.auth.guards.central')` — renamed from `auth.defaults.guards.context.central` during the package extraction (better-dx.md Phase 0): a package key inside a framework config file could carry no package default, so every consumer had to hand-write it before login worked at all. `Nvade\Numerosis\Enums\Tenancy\Context::guard()` is the one place that reads the key now (`Config::string("numerosis.auth.guards.{$this->value}")`) — read through the enum, don't re-interpolate the string at a new call site.

- **`Nvade\Numerosis\Concerns\TenancyAwareGuard` deleted 2026-08-02 — was one-liner wrapping `Auth::getDefaultDriver()`, not worth trait indirection.** Grepped callers before dropping: `LoginUser` and `Authenticate` each called `$this->guard()` once, inlined to `Auth::getDefaultDriver()` / `$this->authManager->getDefaultDriver()` at their one call site. `Livewire\Invitations\Accept` composed the trait but never called `guard()` at all — dead `use` statement, just removed. `IsUserAuthenticated` never used it (stale claim in an earlier version of this bullet — check actual callers with grep, not this file, before trusting a "N callers" count). If a *second* real caller of "current guard name" shows up again, re-add the trait then; one real line at each of two call sites doesn't need a shared abstraction.

- **Policies must not pass guard to Spatie.** `$user->hasRole([...])` and `$user->hasPermissionTo(...)` with no second argument make Spatie resolve guard from *model* (`Guard::getNames()`) — correct source. Seven policies used to pass `$this->guard()` (ambient default) — agrees with model on every normal path, diverges exactly where it matters: `CentralUser` evaluated inside tenant context (as `Authenticate::authenticate()` does) checked against tenant roles it can never hold. Model always knows own guard; ambient default only knows request.

- **Spatie guard name is per-model, already correct — don't "fix" to context-dependent.** `CentralUser::guardName()` returns `'web'`, `Tenant\User::guardName()` returns `['tenant']`, matches seeded data exactly: `RoleAndPermissionSeeder` writes central roles with `guard_name = 'web'`, `Tenant\PermissionAndRoleSeeder` writes tenant roles with `guard_name = 'tenant'`. Per-model *more* correct than context-dependent here: `Authenticate::authenticate()` operates on `CentralUser` while tenancy initialized — context-derived guard would hand that user tenant roles. Shared base `Nvade\Numerosis\Models\User` is `abstract`, so any `guardName()` on it unreachable; it carried hardcoded `'tenant'`, deleted, so future subclass falls back to Spatie config mapping (`Guard::getConfigAuthGuards()` matches `auth.guards.*.provider` models against class) instead of silently inheriting wrong guard.

- **`CentralUser` resolves *no* policy at all, and the tenant twin resolving one correctly is what hides it.** `Gate::getPolicyFor(Nvade\Numerosis\Models\Central\CentralUser::class)` returns `null`; `Gate::getPolicyFor(Nvade\Numerosis\Models\Tenant\User::class)` returns `Nvade\Numerosis\Policies\UserPolicy`. Two mechanisms both miss: `#[UsePolicy(UserPolicy::class)]` sits on `Tenant\User` only, and **attributes are not inherited** — the shared abstract `Nvade\Numerosis\Models\User` base carries none, so `CentralUser` gets nothing from it. Laravel's name guessing then looks for `Nvade\Numerosis\Policies\Central\CentralUserPolicy`, which does not exist (there is no `src/Policies/Central/` directory). Contrast `Nvade\Numerosis\Models\Central\Role`, which *does* resolve `RolePolicy` — because its parent `Nvade\Numerosis\Models\Role` carries the attribute and Laravel walks up to find it. So "central models have policies" is true for roles/permissions and false for users, which is why the gap reads as impossible. Consequence: authorization for central users in the admin panel never reaches `UserPolicy` — it falls through to Gate's `before`/ability callbacks. **Verify with `Gate::getPolicyFor()` in tinker, not by grepping for the policy class** — the class exists and looks wired.

  ## Suggested better approach

  **Corrected 2026-09-01: the fix this section used to propose does not work.** It said to move `#[UsePolicy(UserPolicy::class)]` onto the abstract `Nvade\Numerosis\Models\User` base "so both subclasses inherit it through the parent walk". **There is no parent walk.** PHP attributes are not inherited, and `Gate::getPolicyFor()` reads them off the class it is handed. Measured directly: `Nvade\Numerosis\Models\Central\Tenant` carries `#[UsePolicy(TenantPolicy::class)]`, `App\Models\Central\Tenant` extends it, and `Gate::getPolicyFor(App\Models\Central\Tenant::class)` returns **null**. Anyone acting on the old text would have moved the attribute up, changed nothing, and believed the class of bug was closed.

  That measurement turned up a live defect bigger than the `CentralUser` gap this section was about. **Every admin resource points at `Numerosis::model(...)`, which on any host using the documented model-override seam is a subclass — so `Central\{Tenant,PaymentPlan,Subscription}` resolve no policy at all, and Filament's non-strict authorization allows when no policy resolves.** A `CentralUser` with zero roles renders `/admin/tenants` and sees the data; confirmed empirically, not inferred. The workbench's `Tenant\{User,Invitation,Module}` subclasses escape it only because someone re-declared `#[UsePolicy]` on each by hand. `CentralModelPolicyResolutionTest` guards precisely this mechanism — its own docblock names both halves — but asserts against `Nvade\Numerosis\Models\Central\*`, one subclass away from what the panel loads. Full table in `.claude/plans/archive/numerosis-consolidation.md`'s "Pick up here" item 4.

  **The fix that does work is to stop depending on the attribute**: register each pairing explicitly at boot against the *resolved* class — `Gate::policy(Numerosis::model(Tenant::class), TenantPolicy::class)` — which follows a host's override automatically and needs no annotation discipline from anyone. Nothing in this package calls `Gate::policy()` today. Annotating the workbench subclasses instead would fix the fixture and leave every real host open.

  The original `CentralUser` trade-off still stands and still blocks that half specifically: granting central users a permission-based policy where nothing is consulted today **changes central-panel behaviour the moment it lands**, and `UserPolicy`'s permission names must exist for `guard_name = 'web'` in `RoleAndPermissionSeeder` or every check throws `PermissionDoesNotExist` rather than denying (see the 500-not-403 bullet below).

- **Missing permission row = 500, not 403.** Spatie `hasPermissionTo()` throws `PermissionDoesNotExist` when no permission of that name exists for guard, instead of returning false. Unseeded DB surfaces as `There is no permission named 'viewAny permissions' for guard 'web'` from whichever policy ran first — reads like guard bug, is not. Check `SELECT COUNT(*) FROM permissions` before investigating guards. `RoleAndPermissionSeeder` (central, `guard_name = 'web'`) was missing from `DatabaseSeeder` for a while, so DBs built by `db:seed` had payment plans but zero permissions.

  **Re-running the seeder on a host with a live Redis-backed permission cache is not enough by itself — the DB and the cache can disagree for the lifetime of every already-running PHP worker.** Adding a new permission context (`modules`, added 2026-08-06 for `ModuleOfferingPolicy`) to `RoleAndPermissionSeeder` and reseeding a host (thin-app) still threw `PermissionDoesNotExist: There is no permission named 'viewAny modules' for guard 'web'` on every page — not just the Modules resource, since Filament evaluates every registered resource's `viewAny` to decide nav-item visibility on *every* page render, so one missing permission 500s the whole panel, not just its own screen. `config('permission.cache.store')` is `default` → `redis` on this host, and Spatie's `PermissionRegistrar` caches the full permission list for `cache.expiration_time` (default 24h) regardless of what the `permissions` table now contains. `php artisan permission:cache-reset` after any reseed that adds/renames a permission context is not optional on a host with a persistent cache store — `tinker` sessions are misleading here because each one is a fresh process that may read a different (or no) cache state than the long-lived web worker actually serving requests, so a tinker check can report `ALLOWED` while the browser still 500s.

  **Fixed 2026-08-28:** `RoleAndPermissionSeeder::run()` now calls `app(PermissionRegistrar::class)->forgetCachedPermissions()` itself, right after `givePermissionTo()`. A host reseeding after adding a permission context no longer needs to separately remember `permission:cache-reset` — the trade-off accepted (a hard dependency on the permission package's cache internals inside the seeder) is worth it given how silent and total the failure mode was otherwise (every page in the panel, not just the one with the new permission).

- **`Permission::additionalActions()` reaches the tenant guard only, and only through a subclass you call yourself.** The two seeders read different methods: `Database\Seeders\Tenant\PermissionAndRoleSeeder` calls `Permission::actionsFor($context)` (defaults **plus** `additionalActions()`), while the central `RoleAndPermissionSeeder` calls `Permission::defaultActions()` directly. So a non-CRUD verb added for a context is seeded on `guard_name = 'tenant'` and silently absent on `web` — which, per the 500-not-403 bullet above, is a 500 the first time a central policy checks it. The module system had this exact split: `purchase modules` existed on the tenant guard and never on the central one. `Permission` is also **not** in `numerosis.models`, so there is no `Numerosis::model()` indirection and both seeders name the class literally; a host's subclass is reached only from a `Tenant\PermissionAndRoleSeeder` subclass bound over the package's. `actionsFor()` was `self::`-bound until 2026-09-03, which made even that impossible — it is `static::` now, covered by `tests/Feature/Models/PermissionActionsTest.php`, verified to fail against `self::`.

- **Panels must pin guard explicitly.** `TenantAdminPanelProvider` sets `->authGuard('tenant')`, `AdminPanelProvider` sets central guard. Panel omitting `authGuard()` rides `auth.defaults.guard` — value that now moves during a request.

- **Resolving the tenant guard at all outside tenant context reads the *central* `users` table, and `SessionGuard::logout()` resolves before it clears.** Second live instance of `ModelNotSyncMasterException` (2026-08-12, thin-app `failed_jobs` id 11; the first was `LoginUser`'s, see `LoginUserTest`'s own regression docblock) — same exception, opposite half of the session, so treat the exception name as "a `Tenant\User` was reached through the wrong context", never as one specific bug. `POST /logout` is registered in `routes/auth.php`, which `routes/web.php` requires, so it serves the **central domain** too; `LogoutUser::handle()` called `$this->tenant()->logout()` unconditionally. `SessionGuard::logout()`'s first line is `$user = $this->user()`, which reads the guard's session key — shared across the apex per `session.domain` — and hands the id to the tenant provider, whose model (`Numerosis::model(Tenant\User::class)`) declares no connection and therefore queries whatever is ambient: the central database. Three things then compound, none of which announce themselves:

  1. It hydrates whichever *central* row holds that primary key — a different person, exactly the id-collision `.ai/rules/tenant-caching.md` documents for the shared session key.
  2. `Tenant\User` has no `SoftDeletes` while `CentralUser` does, so the lookup happily returns a **deleted** central account (the live capture was `users` row 1, `deleted_at` set six days earlier).
  3. Non-empty remember token ⇒ `cycleRememberToken()` ⇒ `$user->save()` **into central `users`**, silently killing that stranger's "remember me". Confirmed by matching the token in the failed job's `getChanges()` against the live central row, not inferred.

  The save fires `SyncedResourceSaved($model, tenant())` with `tenant()` null, so the queued `UpdateSyncedResource` hits `getTenantsForCentralModel()` and throws 20× before landing in `failed_jobs`. **The queue exception is the only visible symptom, and it is the least important one** — the cross-user central write happens whether or not the listener is queued at all. Fixed by `LogoutUser::endTenantSession()`: inside tenancy, an ordinary `logout()`; outside it, forget the guard's session key and recaller cookie directly (`$guard->getName()` / `getRecallerName()`), never resolving a user — the same two lines `Nvade\Numerosis\Http\Middleware\EnsureSessionMatchesTenant` already uses, deliberately duplicated rather than abstracted, per the `TenancyAwareGuard` bullet above. `tests/Feature/Actions/Auth/LogoutUserTest.php` guards both directions; it was verified to fail against the pre-fix file.

  **A regression test for this class is vacuous unless both its write and its read stay on one connection.** The first version created the row as a `CentralUser` (connection `central`, autocommit) and read it back the same way, while the bug writes through the ambient default — under `RefreshDatabase`'s transaction on that default, the two snapshots disagree and the test passed against broken code. It now inserts and asserts with `DB::table('users')` on the default connection. Same trap `.ai/rules/testing.md` records for `assertDatabaseHas`, reached from the opposite direction.

  ## Suggested better approach

  This is the second incident whose root cause is `Nvade\Numerosis\Models\Tenant\User` having no connection of its own — the `UpdateUserLastSeenMiddleware` bullet below already proposed pinning it, and each new instance is more evidence for that fix than for another call-site guard. Pinning it would turn all three failure modes above into an immediate "no tenant connection configured" error at the point of the mistake. The cost is real and is why it still hasn't been done: the error would surface *during logout*, i.e. a 500 on a route users hit while already confused, so pinning the model has to land together with the guard here (which no longer resolves a user at all outside tenancy), not instead of it.

- `LogoutUser` logs out both guards by name via `numerosis.auth.guards.{central,tenant}` (`Config::string()`, not `Config::get($key, $fallback)` — a fallback turns a renamed key into silently wrong behaviour instead of an exception, which is what caught the original version of this bug: it read `auth.guards.context.*`, a key that didn't exist, and fell back to a guessed `'central'` name that didn't match the real `'web'` guard, so logout missed the active session). `HostConfig` doesn't touch these two keys directly — they come from `config/numerosis.php`'s own `'auth' => ['guards' => ['central' => 'web', 'tenant' => 'tenant']]` defaults, deep-filled by `NumerosisServiceProvider::packageRegistered()` if a host's override file omits them.

- **Do not bind user or tenant models into container.** `AppServiceProvider` used to bind `CentralUser`, `Tenant\User`, `Tenant` to closures returning current authenticated user / current tenant, two as *singletons*. That caches request-scoped identity for container lifetime (fine under FPM, cross-user leak under Octane), makes guests a `TypeError` instead of auth failure because closures declare non-nullable returns, and hijacks every `Tenant $tenant` or `CentralUser $user` type-hint the container fills. Use `GetAuthenticatedUser::run()` (typed `?User`, better for PHPStan than `auth()->user()`) and stancl's `tenant()` helper.
- **The invariant holds on `initialize()`, not for the whole request — code that must have the tenant guard has to name it.** `AuthGuardBootstrapper` runs once per `tenancy()->initialize()`, and stancl short-circuits a second `initialize()` for the *same* tenant, so the bootstrapper does not re-run. Anything that calls `Auth::shouldUse()` after that point — Filament, a package, a test's `actingAs($user, 'web')` — moves the default guard for the rest of the request with nothing to move it back. `UpdateUserLastSeenMiddleware` resolved `GetAuthenticatedUser::run()` with no argument and, on a second request in an already-initialized process, got a `CentralUser`; it then wrote `last_seen_at` to the *central* `users` table, which has no such column (`Unknown column 'last_seen_at' in 'field list'`, connection `central`). It now resolves the tenant guard explicitly, via `Nvade\Numerosis\Enums\Tenancy\Context::Tenant->guard()` (reads `numerosis.auth.guards.tenant` — renamed from `auth.defaults.guards.context.tenant` during the package extraction, see the `web` *is* central guard bullet above). Treat the ambient default as "probably right" — fine for views and policies, not for anything that writes to a per-context table. `tests/Feature/Http/Middleware/UpdateUserLastSeenMiddlewareTest::test_it_never_writes_last_seen_onto_a_central_user` guards it.

  ## Suggested better approach

  The failure mode is that a tenant-only write silently retargets the central connection. Two structural fixes, either of which kills the class rather than this instance: give `Nvade\Numerosis\Models\Tenant\User` a `protected $connection = 'tenant'`-equivalent guard so a central model can never satisfy a tenant-model write path, or type the middleware against `Nvade\Numerosis\Models\Tenant\User` and skip when the resolved user is anything else — a `?Tenant\User` return is checkable by PHPStan, while `?User` (the shared abstract base) is not. The trade-off is that `GetAuthenticatedUser` stays context-agnostic, so each tenant-only caller has to narrow for itself.

- **Never spell a guard name as a literal, in a route file or a controller.** `numerosis.auth.guards.{central,tenant}` default to `'web'`/`'tenant'`, which is exactly why a literal looks correct forever and breaks only for the host who renamed one. `routes/web.php` built `auth:web` into a group, `routes/tenant.php` had `tenancy.auth:tenant`, `Numerosis::broadcasting()` had `auth:tenant` with a docblock arguing it was deliberately fixed, and three invitation/OAuth controllers called `Auth::guard('web')` directly. All read the config key now. The route files read it once at registration time into a local, which is correct: routes are built per boot and the guard cannot change per request.

  What is genuinely fixed is *which* guard, never its name. `broadcasting()` (removed along with the package's whole broadcasting seam — see `package-boundaries.md`) had to use the tenant guard because authenticating presence channels against the central one leaks them across tenants; that argument said nothing about whether the name was configurable.

  The failure is quiet in the worst way. Route middleware resolves a guard holding nobody, so `ShowInvitationController` read every visitor as a guest and bounced them through login forever, and `AcceptInvitationController` got `null` where its docblock annotated a `CentralUser`. **No other test in the suite renames a guard**, so nothing else can catch a reintroduced literal. `tests/Feature/Auth/RenamedCentralGuardTest.php` renames `numerosis.auth.guards.central` to `host_central` in `getEnvironmentSetUp()` and was verified to fail (3 of its 4 cases) against the literals it replaced.
