# Filesystem Tenancy

- **`config('tenancy.filesystem.root_override')` for `local` stale vs Laravel 11 private-by-default local disk.** `config/filesystems.php` set `'local' => ['root' => storage_path('app/private'), ...]`, but stancl's stubbed `root_override` still pointed at `%storage_path%/app/` (one level too high — missing `/private/`) from before that Laravel convention existed. Under tenant context, `FilesystemTenancyBootstrapper` replaces disk's root with this template, so every tenant-context request looked for `local`-disk files one directory above where they actually live. Now `'local' => '%storage_path%/app/private/'`, matching base config.

- **Livewire's temporary-upload endpoint (`livewire/upload-file`) never runs tenant-identified, but page validating upload usually does — and `local`'s root tenant-suffixed, so two disagree on file location.** Livewire registers that route (and generic `livewire/update` one) directly via own service provider with only `web` middleware group; never passes through `routes/tenant.php`, so never gets `tenancy.identification`. `bootstrap/app.php` shows why: central routes are `Route::middleware('web')->domain($domain)->group(routes/web.php)`, tenant routes separate `Route::middleware('tenant')->group(routes/tenant.php)` (`tenant` = `web` + `tenancy.identification` + …) — Livewire's auto-registered routes in neither group. Filament panel page's own save request *is* tenant-identified (Filament routes own Livewire updates through per-panel route registered inside tenant-domain group, not generic `livewire/update`). So upload always writes under central, un-suffixed `local` root (`storage/app/private/livewire-tmp/…`), while tenant-panel page's server-side validation of same field resolves `local`'s root as `storage/tenant<id>/app/private/…` — directory file never written to. Failure reads as validation error (`"The logo field must be a file of type: image/*."`, Laravel default `mimetypes` rule message) because `TemporaryUploadedFile::getMimeType()` can't find file at wrong path — not 404 or 500, nothing hints "wrong directory."

  Fixed: give Livewire's temp uploads own disk (`config('filesystems.disks.livewire')`, same physical root as `local`, `storage_path('app/private')`) that is **not** listed in `config('tenancy.filesystem.disks')`. Root therefore never overridden, stays fixed regardless of tenant context, matching where uploads actually written. `config('livewire.temporary_file_upload.disk')` points at it. `local` stays tenant-suffixed for everything genuinely tenant-isolated (a `FileUpload` field's final stored file, once moved out of `livewire-tmp` — that move happens from tenant-context request, correctly lands under tenant's own suffixed root).

  **Tell, if resurfaces for new upload field:** temp file physically exists (check `storage/app/private/livewire-tmp/`), its `.json` sidecar records right `type`, `finfo`/`file` agree real image — but Filament still reports `mimetypes`-style rejection. That combo means validating request resolved different disk root than request that wrote file, not that file itself bad. Check `config('filesystems.disks.local.root')` inside vs outside `$tenant->run()` before assuming upload itself broken.

## Suggested better approach

`livewire` disk duplicates `local`'s root by hand, drifts if `local`'s definition ever changes. Cleaner long-term fix: have Livewire's disk reference derive from `config('filesystems.disks.local')` directly (resolved once at boot, before any tenant bootstrapper can touch it) rather than hand-maintained duplicate — not done here, avoids coupling `config/livewire.php` to filesystem config internals for single value.
