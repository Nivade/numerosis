# PHPStan

- **There is one config, `phpstan.neon.dist`, and one baseline. The two-leg split is gone.** From 2026-08-30 to 2026-08-31 this repo carried `phpstan-common.neon` + `phpstan.neon.dist` (stable) + `phpstan-dev-master.neon.dist`, two baselines, and two hand-written reflection stubs under `.phpstan/`. All of it went with the dual-version tenancy layer (`.claude/rules/stancl-tenancy-v4.md`). **Two findings from it outlive the files and apply to any future version-straddling analysis:**

  **A `scanFiles` stub shadows the real class; it does not merge with it.** That is why two stubs could never both be loaded. Measured 2026-08-30: running the stable config with dev-master installed made the dev-master stub's deliberately-trimmed `Stancl\Tenancy\Database\DatabaseConfig` replace the real one, so every `->database()->getName()` / `->manager()` in this package reported `method.notFound` — five call sites, zero defects, and it read exactly like a genuine API break. That shadowing accounted for most of the 49 "real" errors that first run reported.

  **A stub must copy the real signature exactly, including nullability.** `DatabaseConfig::getName()` is `?string` on v3 and `string` on dev-master; declaring the v3 stub's as `string` turned this package's own `?? throw` and `!== null` guards into `nullCoalesce.expr` / `notIdentical.alwaysTrue` "always true" reports — a stricter-than-real stub makes the analysis wrong in the opposite direction.

- **A regenerated baseline is not automatically safe — diff it against the old one before trusting it.** Regenerating from empty baselines *everything*, including a regression the change just introduced. After the dual-version deletion the baseline went 199 entries / 353 errors → 200 / 387, and the only check that made that number meaningful was pairing `(message, path)` between old and new: 33 added, 32 removed, **none of them in `src/`** — all documented `tests/` noise (the Larastan host-subclass false positives below, plus test-idiom `property.nonObject`). A new `src/` entry in that diff would have been a real defect being papered over.

- **The dev-master leg found a real bug the whole test suite could not, and that is the argument for analysing an unreachable code path at all.** `PreservingPathTenantResolver` read `PathTenantResolver::$tenantParameterName` — a v3 public static **property** that dev-master replaced with a static **method**. On dev-master that is a fatal `Error: Access to undeclared static property`, not a type complaint. Nothing caught it because the only caller is a real HTTP request in path mode, which is untestable from console (`.claude/rules/identification-modes.md`). The code is back to reading the v3 property directly (v3-only package now), and `tests/Feature/Resolvers/PreservingPathTenantResolverTest` still drives the resolver directly. **Treat "the suite is green" as insufficient — run PHPStan too, for exactly the code paths the suite cannot reach.**

- **If a version-conditional member ever comes back, reach it through `is_callable()`/`get_class_vars()`, not `Class::method()`/`Class::$prop`** — both branches get analysed whichever version is installed. `method_exists()` + `call_user_func()` is *not* enough: PHPStan still rejects the array callable where the method is absent (`Parameter #1 $callback of function call_user_func expects callable(): mixed, array{...} given`). `is_callable()` narrows and is accepted; its cost is a `function.alreadyNarrowedType` where the method *does* exist, i.e. one baseline entry rather than a code change. Same family as the canonical-branch flattening recorded for conditionally-declared classes in `.claude/rules/stancl-tenancy-v4.md`.

- **Level 9 run over `src`, `config`, `database`, `tests`, `workbench` — no per-path scoping.** Config file is `phpstan.neon.dist` now (not `phpstan.neon` — package repo ships the `.dist`, a consuming host would layer its own `phpstan.neon` on top), `paths: [src, config, database, tests, workbench]`, `level: 9`, none pinned lower. `phpstan-baseline.neon` grandfathers violations that existed when written — **200 `message:` entries / 387 errors as of 2026-08-31**, after the dual-version deletion regenerated it (was 216 on 2026-08-29, 230 earlier that day, and 44 when this bullet was first written). Don't take any of those as current without recounting (`grep -c 'message:' phpstan-baseline.neon`). Don't assume green run = zero level-9 violations — check baseline size, not just exit code. Shrinking it ordinary cleanup, not prereq for anything (see `.claude/rules/testing.md`).

- **The `Internal error: Could not write data to cache file` under `build/phpstan/cache/` is a uid problem, not a PHPStan problem, and there is a one-line way around it that does not need Sail.** Cache entries there are owned by a different uid (consistent with the container-uid note in `.claude/rules/tenant-provisioning.md`'s "Local environment" section), so a plain `vendor/bin/phpstan analyse` aborts with `⚠️ Result is incomplete because of severe errors` after ~14 errors and reports nothing trustworthy. **This repo has no Sail** (see `.claude/rules/testing.md`) — the earlier advice to re-run through `vendor/bin/sail exec` was wrong for it. Point PHPStan at a writable `tmpDir` instead:

  ```bash
  printf 'includes:\n  - %s/phpstan.neon.dist\nparameters:\n  tmpDir: /tmp/phpstan-audit\n' "$PWD" > /tmp/phpstan-audit.neon
  php -d memory_limit=2G vendor/bin/phpstan analyse -c /tmp/phpstan-audit.neon --no-progress
  ```

  The `includes:` path must be absolute — a relative `phpstan.neon.dist` resolves against the config file's own directory (`/tmp`), not the cwd, and fails with `File '/tmp/phpstan.neon.dist' is missing or is not readable`.

  **The same relative-path rule applies to the baseline, and there it fails silently instead of loudly.** A baseline's `path:` entries resolve against *the baseline file's own directory*, so copying `phpstan-baseline.neon` to `/tmp` to diff two trees against it makes every pattern match nothing — PHPStan then reports the entire baselined set as live errors (387 on one tree, 134 on another, both meaningless). Keep any comparison baseline **in the repo root**, next to the real one, and delete it afterwards. Tell: an error count far above what the baseline holds, with no obvious cause.

- **Measured 2026-08-29 with the invocation above, after the Phase-0 cleanup: 0 errors outside the baseline, which is now 216 entries (from 230).** The run is green on this branch, so the baseline does its job again: a rename or a moved vendor class shows up as a *new* hard error. **Before blaming a PHPStan error on your work, diff the count against `git stash`,** the same way `.claude/rules/testing.md` says to baseline a suspicious test failure.

  Getting there cleared 28 errors and removed 16 baseline entries that had gone stale, then added exactly 2. Patterns worth reusing:

  - **A stale baseline entry reports as `ignore.unmatched`, not as silence.** Fixing code surfaces them, and they are load-bearing noise — remove them rather than leaving them. Drive the removal from PHPStan's own output rather than hand-written patterns: the messages are pre-escaped regexes (`\:\:`, `\\\\`), and hand-matching them gets the backslash count wrong in a way that silently deletes nothing or too much. Parse `Ignored error pattern (#^...$#) ... in path (\S+) was not matched` and match those pairs against the baseline's own `message:`/`path:`.
  - **`treatPhpDocTypesAsCertain: false` makes `readonly` collections read as permanently empty.** A `private readonly Collection $x` assigned `new Collection` in the constructor is pinned to the constructor expression's type, `Collection<*NEVER*, *NEVER*>` — so every later `isNotEmpty()` is reported as always-false even though `push()` fills it. A property-level `@var Collection<int, T>` does not override it; dropping `readonly` does. Hit in `src/Testing/FakeCheckoutGateway.php`.
  - **A factory whose parent declares no `@extends Factory<TModel>` poisons every fixture's type.** `Nvade\Numerosis\Database\Factories\Central\SubscriptionFactory` extended Cashier's `SubscriptionFactory`, which extends `Factory` with no generic — so `Subscription::factory()->make()` was a bare `Model` and every call passing a fixture to a typed parameter was an error. Fixed by extending `Illuminate\...\Factory` directly with `@extends Factory<Subscription>` (Cashier's state helpers were all unused). Note this resolves through the model's `#[UseFactory]`, so the *factory's* generic is what matters, not the model's.
  - **`?->` chained onto a laravel-actions `::run()` is not credited with handling null.** `GetAuthenticatedUser::run()?->id` reported `Cannot access property $id on User|null`; assigning to a variable first and then using `?->` on it is clean. Same shape will recur on any `SomeAction::run()?->x`.
  - **Contracts may not reference `Nvade\Numerosis\Models` — `ArchTest` enforces it, and PHPStan will happily suggest the violation.** Narrowing `Contracts\Billing\SubscriptionRepository` to the package's `Subscription` model fixed three type errors and broke `arch('billing contracts do not depend on app models')`. The contract stays on Cashier's base class; callers needing a package-added column (`payment_plan_id`) narrow with `instanceof` at the call site. **Run `--filter=ArchTest` after any type-narrowing pass over `src/Contracts`.**

- **Two errors are baselined deliberately, and neither is a code defect — both are artifacts of the application Larastan boots for analysis differing from the one the tests run.** Do not "fix" the code to chase them.

  - `src/Livewire/Billing/Checkout.php` — `$view of function view expects view-string|null`. Larastan's `ViewStringType` literally calls `view()->exists()` against its own booted app, and **this package's service provider is never registered there**: a root package is not discovered by `PackageManifest` (which reads `vendor/composer/installed.json`), so no `numerosis::` view resolves. 15 sibling entries for the same message were already in the baseline for the same reason; this was the 16th, unbaselined only because the file changed after the baseline was generated.

    Registering `Nvade\Numerosis\NumerosisServiceProvider` in `testbench.yaml`'s `providers:` **does** fix all 16 and makes 36 further baseline entries stale — and was tried and reverted, because it also surfaces ~66 new false positives: with the provider booted, Larastan resolves models through `Numerosis::model()`/`guessFactoryNamesUsing()`'s app-namespace preference, and every test that hints `App\Models\Central\*` (107 files do, deliberately, to exercise the host-subclass mechanism) reports the package base class being passed where the subclass is expected. Net worse. Revisit only with a way to teach Larastan the factory redirection.
  - `tests/Feature/Support/NumerosisSeamTest.php` — `Unreachable statement`. Larastan resolves `ExceptionHandler::class` to `NunoMaduro\Collision\Adapters\Laravel\ExceptionHandler` (Collision is a dev dependency and binds itself in the analysis app), which does not extend `Illuminate\Foundation\Exceptions\Handler` — so the test's `throw_unless($handler instanceof Handler, ...)` guard looks like it always throws. At runtime the handler *is* the framework `Handler` and the test passes. Confirmed with `\PHPStan\dumpType()`; `app()`, `app()->make()` and `resolve()` all resolve identically, so there is no type-honest way to express it.

- **`treatPhpDocTypesAsCertain: false` deliberate, not level-9 side effect.** Docblock shape = claim about data, not runtime-enforced — several of ours describe JSON columns and webhook payloads nothing validates on way in. Left on, PHPStan treats defensive guard against documented shape as "always true" (dead code), pushes toward deleting the guard that's whole point. Native PHP types still treated certain; only level-9 mixed checks affected.

- **Mixed-typed blob consumed multiple places gets one shared type alias, not guard at every call site.** `Plan::metadata(): array<string, mixed>` forced every consumer re-narrow whatever pulled out. Fixed once as `PlanMetadata` type alias declared in `phpstan.neon`, shared by both `Plan` implementations and both consumers. New JSON/array blob gains second consumer add alias instead of duplicating narrowing logic — that duplication exactly what let two copies drift first place.

- **Read config through `Config::string()`/`array()`/`integer()`, not bare `config()`.** `config()` returns `mixed`; typed accessors fail loudly if key missing or wrong shape instead silently propagating `mixed` level 9 then flags at every downstream use. Also used in `LogoutUser` per `.claude/rules/auth-guards.md` — same reasoning, same pattern, use anywhere key known exist.

- **Two behaviour changes shipped as side effect chasing type errors, not separate bug fixes — both worth knowing if either area misbehaves.** `UpdateUserStatus` used swallow missing tenant id, broadcast empty string; now fails loudly instead. `PruneOrphanedTenantDatabases` used coerce unreadable schema name; now skips names it can't prove strings — since issues `DROP DATABASE`, unrecognised value must fall out of orphan list, never into it.
