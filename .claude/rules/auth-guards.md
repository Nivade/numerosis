# Auth Guards

- **Invariant: central domain default guard = central guard, inside tenant = tenant guard.** Enforced by `App\Services\Tenancy\Bootstrappers\AuthGuardBootstrapper`, registered in `config('tenancy.bootstrappers')`, calls `Auth::shouldUse()` on bootstrap, restores previous guard on `revert()`. `AuthManager::shouldUse()` rewrites both `auth.defaults.guard` *and* manager's `userResolver`, so `auth()->user()`, `$request->user()`, `@auth`, `Gate`, policies all follow automatically. Before this: rule was convention only — code opting into `TenancyAwareGuard` got it right, everything else silently resolved `CentralUser` on tenant domains.

- **`web` *is* central guard.** No guard named `central` — one existed alongside `web`, backed by duplicate `central` provider over same `CentralUser` model, deleted because nothing called `Auth::guard('central')` and two session guards over one model = user authenticated under one, not other. `web` keeps Laravel's default name so framework/package defaults land on it. App code names it `config('numerosis.auth.guards.central')` — renamed from `auth.defaults.guards.context.central` during the package extraction (better-dx.md Phase 0): a package key inside a framework config file could carry no package default, so every consumer had to hand-write it before login worked at all. `App\Enums\Tenancy\Context::guard()` is the one place that reads the key now (`Config::string("numerosis.auth.guards.{$this->value}")`) — read through the enum, don't re-interpolate the string at a new call site.

- **`App\Concerns\TenancyAwareGuard` deleted 2026-08-02 — was one-liner wrapping `Auth::getDefaultDriver()`, not worth trait indirection.** Grepped callers before dropping: `LoginUser` and `Authenticate` each called `$this->guard()` once, inlined to `Auth::getDefaultDriver()` / `$this->authManager->getDefaultDriver()` at their one call site. `Livewire\Invitations\Accept` composed the trait but never called `guard()` at all — dead `use` statement, just removed. `IsUserAuthenticated` never used it (stale claim in an earlier version of this bullet — check actual callers with grep, not this file, before trusting a "N callers" count). If a *second* real caller of "current guard name" shows up again, re-add the trait then; one real line at each of two call sites doesn't need a shared abstraction.

- **Policies must not pass guard to Spatie.** `$user->hasRole([...])` and `$user->hasPermissionTo(...)` with no second argument make Spatie resolve guard from *model* (`Guard::getNames()`) — correct source. Seven policies used to pass `$this->guard()` (ambient default) — agrees with model on every normal path, diverges exactly where it matters: `CentralUser` evaluated inside tenant context (as `Authenticate::authenticate()` does) checked against tenant roles it can never hold. Model always knows own guard; ambient default only knows request.

- **Spatie guard name is per-model, already correct — don't "fix" to context-dependent.** `CentralUser::guardName()` returns `'web'`, `Tenant\User::guardName()` returns `['tenant']`, matches seeded data exactly: `RoleAndPermissionSeeder` writes central roles with `guard_name = 'web'`, `Tenant\PermissionAndRoleSeeder` writes tenant roles with `guard_name = 'tenant'`. Per-model *more* correct than context-dependent here: `Authenticate::authenticate()` operates on `CentralUser` while tenancy initialized — context-derived guard would hand that user tenant roles. Shared base `App\Models\User` is `abstract`, so any `guardName()` on it unreachable; it carried hardcoded `'tenant'`, deleted, so future subclass falls back to Spatie config mapping (`Guard::getConfigAuthGuards()` matches `auth.guards.*.provider` models against class) instead of silently inheriting wrong guard.

- **`CentralUser` resolves *no* policy at all, and the tenant twin resolving one correctly is what hides it.** `Gate::getPolicyFor(App\Models\Central\CentralUser::class)` returns `null`; `Gate::getPolicyFor(App\Models\Tenant\User::class)` returns `App\Policies\UserPolicy`. Two mechanisms both miss: `#[UsePolicy(UserPolicy::class)]` sits on `Tenant\User` only, and **attributes are not inherited** — the shared abstract `App\Models\User` base carries none, so `CentralUser` gets nothing from it. Laravel's name guessing then looks for `App\Policies\Central\CentralUserPolicy`, which does not exist (there is no `app/Policies/Central/` directory). Contrast `App\Models\Central\Role`, which *does* resolve `RolePolicy` — because its parent `App\Models\Role` carries the attribute and Laravel walks up to find it. So "central models have policies" is true for roles/permissions and false for users, which is why the gap reads as impossible. Consequence: authorization for central users in the admin panel never reaches `UserPolicy` — it falls through to Gate's `before`/ability callbacks. **Verify with `Gate::getPolicyFor()` in tinker, not by grepping for the policy class** — the class exists and looks wired.

  ## Suggested better approach

  Move `#[UsePolicy(UserPolicy::class)]` onto the abstract `App\Models\User` base so both subclasses inherit it through the parent walk, and drop the now-redundant attribute from `Tenant\User`. That kills the class of bug rather than this instance: any future `App\Models\*\User` subclass is covered by construction instead of by someone remembering to annotate it. The trade-off is real and needs a decision rather than a patch — **this grants central users a permission-based policy where today nothing is consulted**, so central-panel behaviour changes the moment it lands, and `UserPolicy`'s permission names must exist for `guard_name = 'web'` in `RoleAndPermissionSeeder` or every check throws `PermissionDoesNotExist` (see the 500-not-403 bullet below). Not done here for that reason.

- **Missing permission row = 500, not 403.** Spatie `hasPermissionTo()` throws `PermissionDoesNotExist` when no permission of that name exists for guard, instead of returning false. Unseeded DB surfaces as `There is no permission named 'viewAny permissions' for guard 'web'` from whichever policy ran first — reads like guard bug, is not. Check `SELECT COUNT(*) FROM permissions` before investigating guards. `RoleAndPermissionSeeder` (central, `guard_name = 'web'`) was missing from `DatabaseSeeder` for a while, so DBs built by `db:seed` had payment plans but zero permissions.

  **Re-running the seeder on a host with a live Redis-backed permission cache is not enough by itself — the DB and the cache can disagree for the lifetime of every already-running PHP worker.** Adding a new permission context (`modules`, added 2026-08-06 for `ModuleOfferingPolicy`) to `RoleAndPermissionSeeder` and reseeding a host (thin-app) still threw `PermissionDoesNotExist: There is no permission named 'viewAny modules' for guard 'web'` on every page — not just the Modules resource, since Filament evaluates every registered resource's `viewAny` to decide nav-item visibility on *every* page render, so one missing permission 500s the whole panel, not just its own screen. `config('permission.cache.store')` is `default` → `redis` on this host, and Spatie's `PermissionRegistrar` caches the full permission list for `cache.expiration_time` (default 24h) regardless of what the `permissions` table now contains. `php artisan permission:cache-reset` after any reseed that adds/renames a permission context is not optional on a host with a persistent cache store — `tinker` sessions are misleading here because each one is a fresh process that may read a different (or no) cache state than the long-lived web worker actually serving requests, so a tinker check can report `ALLOWED` while the browser still 500s.

  ## Suggested better approach

  `RoleAndPermissionSeeder::run()` could call `app(PermissionRegistrar::class)->forgetCachedPermissions()` itself, right after writing the rows — the seeder already knows it just changed the set of permissions that exist, so it shouldn't require every caller to separately remember the cache exists. The trade-off is that the seeder would gain a hard dependency on the permission package's cache internals rather than just its Eloquent models; worth it given how silent and total the failure mode is otherwise (every page in the panel, not just the one with the new permission).

- **Panels must pin guard explicitly.** `TenantAdminPanelProvider` sets `->authGuard('tenant')`, `AdminPanelProvider` sets central guard. Panel omitting `authGuard()` rides `auth.defaults.guard` — value that now moves during a request.

- `LogoutUser` logs out both guards by name via `numerosis.auth.guards.{central,tenant}` (`Config::string()`, not `Config::get($key, $fallback)` — a fallback turns a renamed key into silently wrong behaviour instead of an exception, which is what caught the original version of this bug: it read `auth.guards.context.*`, a key that didn't exist, and fell back to a guessed `'central'` name that didn't match the real `'web'` guard, so logout missed the active session). `HostConfig` doesn't touch these two keys directly — they come from `config/numerosis.php`'s own `'auth' => ['guards' => ['central' => 'web', 'tenant' => 'tenant']]` defaults, deep-filled by `HostConfig::numerosisConfig()` if a host's override file omits them.

- **Do not bind user or tenant models into container.** `AppServiceProvider` used to bind `CentralUser`, `Tenant\User`, `Tenant` to closures returning current authenticated user / current tenant, two as *singletons*. That caches request-scoped identity for container lifetime (fine under FPM, cross-user leak under Octane), makes guests a `TypeError` instead of auth failure because closures declare non-nullable returns, and hijacks every `Tenant $tenant` or `CentralUser $user` type-hint the container fills. Use `GetAuthenticatedUser::run()` (typed `?User`, better for PHPStan than `auth()->user()`) and stancl's `tenant()` helper.
- **The invariant holds on `initialize()`, not for the whole request — code that must have the tenant guard has to name it.** `AuthGuardBootstrapper` runs once per `tenancy()->initialize()`, and stancl short-circuits a second `initialize()` for the *same* tenant, so the bootstrapper does not re-run. Anything that calls `Auth::shouldUse()` after that point — Filament, a package, a test's `actingAs($user, 'web')` — moves the default guard for the rest of the request with nothing to move it back. `UpdateUserLastSeenMiddleware` resolved `GetAuthenticatedUser::run()` with no argument and, on a second request in an already-initialized process, got a `CentralUser`; it then wrote `last_seen_at` to the *central* `users` table, which has no such column (`Unknown column 'last_seen_at' in 'field list'`, connection `central`). It now resolves the tenant guard explicitly, via `App\Enums\Tenancy\Context::Tenant->guard()` (reads `numerosis.auth.guards.tenant` — renamed from `auth.defaults.guards.context.tenant` during the package extraction, see the `web` *is* central guard bullet above). Treat the ambient default as "probably right" — fine for views and policies, not for anything that writes to a per-context table. `tests/Feature/Http/Middleware/UpdateUserLastSeenMiddlewareTest::test_it_never_writes_last_seen_onto_a_central_user` guards it.

  ## Suggested better approach

  The failure mode is that a tenant-only write silently retargets the central connection. Two structural fixes, either of which kills the class rather than this instance: give `App\Models\Tenant\User` a `protected $connection = 'tenant'`-equivalent guard so a central model can never satisfy a tenant-model write path, or type the middleware against `App\Models\Tenant\User` and skip when the resolved user is anything else — a `?Tenant\User` return is checkable by PHPStan, while `?User` (the shared abstract base) is not. The trade-off is that `GetAuthenticatedUser` stays context-agnostic, so each tenant-only caller has to narrow for itself.
